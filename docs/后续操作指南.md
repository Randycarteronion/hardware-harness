## 二、回来后 10 分钟验收（按顺序做）

### 1. 环境自检（不需要硬件）

```bash
cd hardware-harness
python -m pytest tests -q        # 应 43 passed
harness list-devices             # 应列出 4 台设备
```

### 2. 插回 ESP32-S3（USB 线直连电脑）——全链路验收

```bash
harness discover                                   # 确认 COM 口出现（vid=1a86）
harness monitor esp32s3_dev --duration 3s          # 应看到 {"rpm":0,...} 行
harness run-test examples/tests/esp32_motor_start.yaml   # 应 PASS，exit 0
```

### 3. 部署迭代演示（B7 新功能，不用重刷固件）

改 `firmware/esp32/micropython/main.py`（比如把 TARGET 改成 900），
然后：

```bash
harness deploy esp32s3_dev firmware/esp32/micropython/main.py
harness run-test examples/tests/esp32_motor_start.yaml   # 断言 >1000 会 FAIL
```

故意 FAIL 一次也有价值：看报告里 `detail.measured`（实测 8xx rpm）
带单位返回 —— 这就是 Agent 自我修复时读的字段。

### 4. 插回 STM32 + ST-Link —— SWD 链路复验 + build→flash 连击

```bash
harness build bluepill_f103                                  # 真 armcc 编译
harness flash bluepill_f103 firmware/stm32/f103_motor_demo/fw.bin \
       --confirm confirm:flash                               # 三道闸 + 向量检查
# 板上 PC13 灯闪 = 成功
```

（遥测需要 USB-TTL 模块，见 `docs/backlog/stm32-telemetry-blocked.md`，
三根线接完跑 `harness monitor bluepill_f103` 即闭环。）

### 5. 把 Agent 真正接上（MCP 或自带大脑）

**路线 A：自带大脑（新增）** —— 不依赖任何 Agent Host：

```bash
# 本地模型（注意：本机 4GB 显存/16GB 内存跑 8B 需先腾内存，见下）
harness agent-serve
harness agent "列出硬件设备并总结"

# 或 DeepSeek API（key 一设即用）
set HARNESS_AGENT_PROVIDER=deepseek
set DEEPSEEK_API_KEY=sk-xxxx
harness agent "跑 examples/tests/motor_start.yaml 并告诉我实测转速"
```

危险操作会暂停问你 y/n；完整对话落盘 `runs/agent_*/transcript.md`。

**本机跑本地 8B 的现实约束（实测）**：4GB 显存 WDDM 下 GPU 卸载全灭；
纯 CPU 需 ≥6GB 空闲内存（当前开发环境只剩 4.3GB）。三条解锁路：
关应用腾内存 / 找渠道下 Qwen3-4B（2.4GB）换 `llama_model` /
换大显存机器。全部细节见 **`docs/模型接入.md`**。

**路线 B：DSH / Claude Code 当 Host** —— mcpServers 配置加：

```json
{
  "mcpServers": {
    "hardware": { "command": "harness-mcp", "args": [] }
  }
}
```

然后对 Agent 说：**"列出可用的硬件设备"** —— 它调
`hardware_list_devices` 返回 4 台。再试一句完整的：
"把 ESP32 的电机目标转速改成 800 并验证" —— 观察 Agent 自己走
monitor → 改 main.py → deploy → run-test → 读报告 → （FAIL）→
调整断言或转速 → 重跑的循环。**这一刻就是项目的最终形态。**

（DSH 说明：`.dsh/settings.yaml` 里本地 llama.cpp 和 DeepSeek 两个
provider 都已配好；Desktop/DSH 目录是空的——GitHub Desktop 拉取
没成功，需要的话重新 clone。DSH↔harness 的对接走上面同一个
mcpServers 配置，详见 docs/模型接入.md 第四节。）

## 三、安全模型速记（给 Agent 配权限时参考）

- **read-only/safe**（monitor / run_test / deploy / build）：Agent 自主
- **destructive**（flash / power_cycle）：必须 `confirm:flash` token，
  Agent 拿不到就得来问你 —— 这是设计好的行为，不是故障
- 烧录另有硬闸：ESP32 比对 MAC、STM32 比对 DeviceID+flash 容量，
  对不上直接拒烧
- 设备锁：同设备跨进程互斥（`~/.hardware-harness/locks/`），
  崩溃自动回收，撞锁报 E_DEVICE_BUSY 并显示占用者

## 四、常见问题速查（详见 lessons.md）

| 症状 | 原因 | 处置 |
|---|---|---|
| "cannot resolve serial port" | 设备没插 | 先 `harness discover` 确认 |
| discover 列出蓝牙 COM 口 | Windows 蓝牙虚拟口 | 无视，匹配永远用 vid/序列号 |
| pyocd "older firmware" | 山寨 ST-Link 老固件 | 设备 yaml 用 `tool: stlink_cli`（已配好）|
| "No ST-LINK detected" | 探针松了/被 IDE 占 | 重插；关 Keil/CubeProg 的 debug 会话 |
| mpremote 首次 cp 失败 | 开口复位竞态 | 已内置重试；持续失败=口被占 |
| 中文输出乱码/崩读线程 | 工具输出 GBK | 已修（errors=replace），复现即回归 |
| ESP32 无输出 | DTR/RTS 按住复位 | 已修（开口释放双线）|
